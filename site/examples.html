示例

简单：v0 → v1 细粒度控制 故障与重开 网页后端流程 换成自己的适配器

源码： tests/scenarios.rs

i 先跑全部四个：cargo test -p n2x-migration-lab --test scenarios。 每个测试使用独立临时目录，不会改动 lab 的 data/。

简单：v0 → v1

一条边包含建表、导入 4 条用户、搬迁目录、删除源目录和校验。 适合先确认“步骤、提交、版本推进”如何组合。

scenario_simple_single_edge Lab::run_to 
cargo test -p n2x-migration-lab --test scenarios scenario_simple_single_edge -- --nocapture
let dir = tempfile::tempdir()?;
let mut lab = Lab::open(dir.path())?;
assert_eq!(lab.state().await?["version"], "v0");

let state = lab.run_to("v1").await?;

assert_eq!(state["version"], "v1");
assert_eq!(state["sql_version"], 1);
assert_eq!(state["tables"]["users"]["columns"], json!(["id", "first_name", "last_name"]));
assert_eq!(state["tables"]["users"]["rows"].as_array().unwrap().len(), 4);
assert_eq!(state["files"]["a_exists"], false);
assert_eq!(state["files"]["b"].as_array().unwrap().len(), 4);
预期 version v1 sql_version 1 users 4 行 files.a false files.b 4 项

这里只有一个版本边，所以版本从 v0 直接到 v1。 所有 Step 完成后才提交版本；中途失败时版本保持 v0。

细粒度控制

区分三种粒度：tick 是一条协议命令，step 推进到下一个业务步骤完成，run_to 连续执行到目标版本。

scenario_tick_pause_resume Lab::step / tick / control 
cargo test -p n2x-migration-lab --test scenarios scenario_tick_pause_resume -- --nocapture
let mut lab = Lab::open(dir.path())?;
lab.start("v1").await?;

// 只完成一个业务步骤，版本仍是 v0。
let after_step = lab.step().await?;
assert_eq!(after_step["version"], "v0");

// 在下一个安全边界暂停。
lab.control(n2x::Control::Pause)?;
let mut state = lab.state().await?;
while state["run"]["status"] != "Paused" {
    state = lab.tick().await?;
}
assert_eq!(state["version"], "v0");

// 继续，直到整条边完成。
lab.resume().await?;
let mut state = lab.state().await?;
while state["run"]["status"] != "Completed" {
    state = lab.tick().await?;
}
assert_eq!(state["version"], "v1");
执行序列 start version v0, next_command 存在 step version v0, 一个 Step 完成 Pause version v0, status Paused Resume + tick version v1, status Completed

step 是 lab 的辅助方法，内部循环调用 tick 直到步骤完成。 库本身只暴露 tick 和 run；宿主可以用它们实现自己的调度粒度。

故障与重开

lab 可以注入一次 v2 写入事务回滚。故障后版本停在 v1， 新表没有数据；显式恢复后从失败处继续，而不是重跑整个 v1。

scenario_fault_and_recovery Lab::fault / resume / reopen 
cargo test -p n2x-migration-lab --test scenarios scenario_fault_and_recovery -- --nocapture
let mut lab = Lab::open(dir.path())?;
lab.run_to("v1").await?;

// 让下一次 v2 写入回滚一次。
lab.fault.set(true);
let failed = lab.run_to("v2").await?;
assert_eq!(failed["version"], "v1");
assert_eq!(failed["run"]["status"], "Failed");
assert_eq!(failed["run"]["last_error"]["code"], "lab.business.rolled_back");
assert!(failed["tables"]["users_v2"]["rows"].as_array().unwrap().is_empty());

// 修复后显式恢复，再从失败处继续。
lab.resume().await?;
let recovered = lab.run_to("v2").await?;
assert_eq!(recovered["version"], "v2");

// 丢弃执行器，重开同一个状态目录，继续到 v3。
let mut reopened = lab.reopen()?;
let v3 = reopened.run_to("v3").await?;
assert_eq!(v3["version"], "v3");
assert!(v3["schema"].as_array().unwrap().iter().any(|i| i["name"] == "idx_users_name"));
预期 v1 完成 version v1 注入故障 next v2 write rolled back 失败后 version v1, status Failed, users_v2 0 行 resume + v2 version v2, users 4 行 reopen + v3 version v3, idx_users_name 存在 回退请求 n2x.version.rollback_unsupported

这个例子覆盖了三个恢复点：写入事务回滚、执行器重开、以及在已提交后继续。 注意版本在失败后仍是 v1，不会假装到达 v2。

网页后端流程

lab 的 HTTP API 是 Lab 方法的一层薄封装。这个示例按网页按钮的顺序 调用同样的方法，覆盖查询、启动、单步、重开、故障、恢复和重置。

scenario_web_backend_flow GET /api/state · POST /api/* 
cargo test -p n2x-migration-lab --test scenarios scenario_web_backend_flow -- --nocapture
cargo run -p n2x-migration-lab   # 网页版：http://127.0.0.1:8427
// GET /api/state
assert_eq!(lab.state().await?["version"], "v0");

// POST /api/start {"target":"v1"}
lab.start("v1").await?;
// POST /api/step
lab.step().await?;

// POST /api/reopen：丢弃执行器，保留状态目录
let mut lab = lab.reopen()?;
assert_eq!(lab.state().await?["executor_loaded"], false);
let v1 = lab.run_to("v1").await?;   // 先恢复活动运行

// POST /api/fault，然后执行 v2
lab.fault.set(true);
let failed = lab.run_to("v2").await?;
assert_eq!(failed["run"]["status"], "Failed");

// POST /api/resume
lab.resume().await?;
let v2 = lab.run_to("v2").await?;
assert_eq!(v2["version"], "v2");

// POST /api/reset：删除数据目录并重新初始化
let root = lab.root.clone();
drop(lab);
std::fs::remove_dir_all(&root)?;
let mut fresh = Lab::open(root)?;
assert_eq!(fresh.state().await?["version"], "v0");
对应的 HTTP 顺序 GET /api/state version v0 POST /api/start {"target":"v1"} POST /api/step 完成一个步骤 POST /api/reopen executor_loaded=false POST /api/fault 下一次 v2 写入回滚 POST /api/resume 继续失败/暂停运行 POST /api/reset 删除并重建测试数据

HTTP 处理器、响应格式和错误码见 main.rs。 服务只监听 127.0.0.1，不包含生产部署功能。

换成自己的适配器

四个示例都使用 lab 的 JSON、SQLite 和目录端口。把其中任何一个替换成你的数据库时， 需要先满足两件事：

  • 写入端能按同一个 OperationId 去重，或者能权威回答“做没做”；
  • Reader 能提供稳定游标和可验证的源视图。
