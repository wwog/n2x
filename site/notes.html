上线前检查

这里列出运行时约束和需要应用自己负责的部分。默认值可以工作，但容量、写入端 契约和单写者边界需要按你的场景确认。

部署前阅读 含默认值 含故障处理步骤

检查项

KV 容量与保留 retire 与归档 写入端契约 持久级别 单写者 没有自动回滚 大数据与 Blob 计划冻结 运行驱动 KV 满了怎么办 不适用场景

KV 容量与保留

Workspace 只保存恢复所需的小状态。当前默认值：

项目默认值调整
KV 文件上限64 MiB；单值 16 MiB；单帧 32 MiBStoreOptions
提交收据每个 Run 最近 128 条with_commit_retention
事件每个 Run 1,000 条with_event_limit
事件总预算整个工作区 20,000 条with_event_budget
计划 / 恢复快照 / 报告每个 Run 一份，直到回收retire_run
! 容量耗尽时提交返回持久化错误，运行停在原地。压缩只回收被覆盖的死数据， 不会删除仍然活着的收据、事件和运行材料。

Migrator::open_native 使用默认 StoreOptions，没有直接暴露 max_bytes。需要修改上限时，自己组合 StateWorkspace 和 StateBackend。

retire 与归档

retire_run(CommitId, RunId, keep_report) 回收已完成运行的计划、 恢复快照、事件、隔离记录、提交日志和收据。约束：

  • 只接受 Completed / CompletedWithRejections；活动、暂停、失败、取消、待处理返回冲突。
  • 必须先 unsubscribe 所有可靠订阅者，否则返回冲突。
  • 报告默认保留；导出后传 keep_report = false 可一并删除。
  • 同一个 CommitId 重试是幂等的。

原生组合在删除前写 state/archive/<run>-<hash>.ndjson 并 fsync； 归档失败时提交返回错误，KV 保持不变。归档按运行幂等，重试不会重复写入。 

{"format_version":1,"run":"...","scope":"...","current":"v1","target":"v1","plan":"<sha256>","retire_commit":"...","archived_at":1730000000000,"entries":7}
{"kind":"plan","key":"n2x/v1/plan/\"...\"","value":{...}}
{"kind":"report","key":"n2x/v1/report/\"...\"","value":{...}}
{"kind":"quarantine","key":"n2x/v1/quarantine/[...]","value":[...]}

归档包含隔离记录，可能含原始敏感数据。按业务数据的保护级别对待 archive/ 目录；它不占 KV 容量，生命周期由应用负责。

写入端契约

框架保证顺序和持久化，不能替适配器实现幂等。写入端需要满足其中之一：

  • 幂等：同一个 OperationId 重复执行，业务效果只产生一次。
  • 可对账：结果不明时能权威查询“做没做”。

必须遵守的细节：

  • 相同 OperationId 不同 request_digest 必须拒绝。
  • 去重凭证与业务效果在同一个事务里保存，保留期覆盖允许的恢复期限。
  • “暂时查不到”不能当成 NotApplied；可能只是还没提交。
  • CheckAction 必须只读；TransformAction 必须确定性。

编译器会检查声明的恢复能力，但无法验证实现真的遵守协议。适配器示例见 fixtures.rs。

持久级别

默认 RunPolicy::durability = Durable：每次工作区提交都要 flush 成功， 引擎才继续发下一个业务命令。

Durability::Memory 跳过 flush，只适合测试或临时运行。 外部副作用仍会发生，但工作区状态不承诺重开恢复；不要用于生产可恢复运行。

单写者

当前只有一个活动写者。原生入口用独立锁文件取得进程级独占权； KV 没有 CAS，也没有跨进程锁，不能用 get + set 假装抢锁。

锁文件不要指向可能被 compact 替换的 state.kv inode。 多写者、fencing、分布式租约不在当前承诺里。

没有自动回滚

失败、暂停、取消都不表示目标端没变。版本权威只在整条边全部确认后推进； 已完成的外部效果不会被自动撤销。

需要清理或撤销时，把它建模成显式的 Task 或 Check， 并声明恢复契约。不要假设“取消”等于“回到起点”。

大数据与 Blob

Transfer 的批次有记录数和内联字节上限。大文件、大导出使用 BlobStore， KV 只保存引用。恢复材料存在时，相关 Blob 不能被提前回收；spool 的引用回收 目前由应用负责。

把整个数据库导出塞进 KV 会撞上单值/帧限制，也会拖慢恢复。

计划冻结

运行开始时会冻结 PlanSnapshot，恢复时重新编译并比较摘要。 修改 Manifest、ActionRef revision、转换函数或能力声明后，恢复返回 PLAN_CHANGED，不会静默使用新行为。

需要改变迁移逻辑时，先结束当前运行，再把“重建计划”当成显式管理操作。

运行驱动

Engine 不自己睡眠、不自己起线程、不内置网络推送。宿主调用 tick / run，用自己的执行器处理唤醒和取消。

通知由调用方拉取（events_after）或从 drain_notices 取走。 可靠订阅要求消费者按 RunId + sequence 去重并 ACK。

KV 满了怎么办

不要直接删 state.kv。按顺序处理：

  1. 读取并导出已完成运行的报告与隔离记录。
  2. unsubscribe 所有可靠订阅者，释放事件历史保护。
  3. retire_run 已完成的运行；一次回收一个，保留报告或按需删除。
  4. 重试原 CommitId：失败的那次提交用同一个 ID 重试。
  5. 确认活键下降：用 n2x-kv 统计或查看器观察，再继续。

收据裁剪依赖引擎只重试当前命令。不要绕过 Migrator 手动重放很旧的 CommitId，那可能用旧状态覆盖新状态。

不适用场景

  • 一次性的小脚本，失败后重跑即可。
  • 需要跨系统两阶段提交或全局锁。
  • 把 KV 当数据仓库或全量导出载体。
  • 需要框架自带后台调度、多写者租约或网络推送。
