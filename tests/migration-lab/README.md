# Migration lab

一个真正使用 n2x 公共入口的本地网页测试服务。JSON、SQLite 与目录端口全部位于此测试
项目，不作为框架业务适配器发布。测试运行不访问项目外的业务数据。

## 启动

在仓库根目录执行：

```sh
cargo run -p n2x-migration-lab
# 不自动打开浏览器 / 更换端口：
cargo run -p n2x-migration-lab -- --no-open --port 8427
```

默认页面：<http://127.0.0.1:8427>，默认数据目录为本项目的 `data/`，已被 Git 忽略。
`--data /absolute/path` 可以指定独立测试目录。服务只监听 127.0.0.1，无生产部署功能。

## 版本和实际资源

| 边 | 行为 | 完成后 |
| --- | --- | --- |
| v0→v1 | 创建 users，导入 JSON，搬迁 a→b，核对后删除 a，校验 | users(id, first_name, last_name)，SQL user_version=1 |
| v1→v2 | 建 users_v2，分批合并姓名，发布新表并校验 | users(id, name)，SQL user_version=2 |
| v2→v3 | 创建姓名索引、校验 | idx_users_name，SQL user_version=3，行数据不变 |

v1 的 JSON 导入和目录搬迁是同一版本边内的不同 Step，全部完成后才提交 v1。
四条初始记录为 Ada Lovelace、Grace Hopper、Alan Turing、Linus Torvalds。
目录包含普通文件、嵌套文件与空目录。

```text
data/
  initialized             初始测试资源已生成的标记，不是迁移版本
  users.json              初始数据，保留以供观察
  users.sqlite            真实数据库，含 _n2x_receipts 去重表
  a/                      初始目录；v1 校验后被删除
  b/                      迁移后的目录
  workspace/
    workspace.lock        防止多个执行器同时迁移；文件存在不等于正在占用
    state.kv              已保存的版本、迁移计划、进度、报告和事件
  observations.jsonl      每条命令后的版本与下一命令
  errors.jsonl            业务与请求错误
```

## 建议操作

1. 首次打开看到 v0。在“逐项观察迁移过程”中选 v1，点击“准备逐项迁移”。此时只准备计划。
2. 多次点击“完成下一项”，依次观察建表、导入全部 JSON、复制目录、清理原目录和校验。
   一个版本包含多个业务项，全部成功后才更新顶部已完成版本。
3. 点击“自动迁移到 v2”，观察两列合并为 name；点击“自动迁移到 v3”，观察新增索引且行数据一致。
4. 在 v3 点击“自动迁移到 v1”，页面显示 `n2x.version.rollback_unsupported`，实际版本保持 v3。
5. 展开“测试失败与重启恢复”，用“清空演示数据，回到 v0”重新开始；直接“自动迁移到 v3”，
   观察执行记录依次确认 v1、v2、v3。
6. 再清空并自动迁移到 v1，点击“让 v2 的下一次写入失败”，然后自动迁移到 v2。
   下一批姓名合并写入被撤销并报错，已完成版本仍为 v1，users_v2 未插入数据。
   点击“准备从失败处重试”，再用“完成下一项”或自动迁移到原目标，完成 v2。
7. 中途点击“模拟重启，保留进度”。数据库、文件和已保存的进度保留；目标会保持为原目标。
   点击“准备逐项迁移”加载进度，再逐项或自动继续。这个按钮重建迁移执行器，不会关闭 HTTP 服务。

重置只在用户明确点击并确认后删除指定测试数据目录。请勿将 `--data` 指向业务目录。
“准备从失败处重试”只恢复调度，不立即执行数据操作，不跳过失败项。测试故障只影响一次 v2 写入，
不是将已经完成的 v2 降级到 v1，也不撤销先前已完成的其他业务项。

“完成下一项”与开发调试区的“推进一次内部动作”粒度不同：一个业务项（Step）可以包含多次内部动作，
例如保存执行意图、读取一批、转换、写入一批、保存进度。逐项执行会推进到下一个业务项完成、
版本确认或停止；内部动作按钮只推进一次框架命令，可能看不到业务数据变化。
内部状态与此按钮放在默认收起的“内部调度详情（开发调试）”中。

页面会根据运行状态禁用暂不可用的按钮。未完成的任务使用原目标；重启后需要先加载进度，才能准备重试。
如果上次写入是否提交尚未确认，页面提示人工核对；本网页没有提交人工核对结论的入口。

直接请求 v3 是自动补齐路径，不是直接忽略 v1/v2。框架支持单独声明捷径边并使用
Route::Explicit 选择；本项目故意保留完整链路来检查每个项目不会遗漏。

## 本地 HTTP API

接口响应为 `{ ok, state }` 或 `{ ok: false, error, state }`。
业务步骤失败也会保存到 `state.run.last_error`、标准报告与 errors.jsonl。
所有操作串行执行，不提供外部服务或通知发送。

| 方法与路径 | 请求 | 用途 |
| --- | --- | --- |
| GET /api/state | 无 | 查询实际 SQL、目录、运行、事件、错误 |
| POST /api/start | {"target":"v1"} | 编译 / 恢复计划 |
| POST /api/tick | {} | 一条协议命令，包含持久化边界 |
| POST /api/step | {} | 到下一个步骤完成 / 版本提交 / 停止 |
| POST /api/run | {"target":"v3"} | 连续执行，补齐路径 |
| POST /api/resume | {} | 显式继续失败 / 暂停运行 |
| POST /api/fault | {} | 注入下一次 v2 写事务回滚 |
| POST /api/reopen | {} | 丢弃执行器、重新打开持久状态 |
| POST /api/reset | {} | 删除并重新生成测试资源 |

SQL 业务变更与 OperationId 凭证在同一 SQLite 事务提交；同步级别 FULL。
目录写入按内容幂等重放；清理前核对 a/b 内容。测试用 Reader 每批核对源摘要，在迁移
期间外部改动源会报错。工作区权威版本与 SQL user_version 分别展示，方便观察中间窗口。

## 数据表迁移与提交凭证

v2 先创建 `users_v2(id, name)`，由 Reader 读取旧 `users`，Transform 在 Rust 中合并姓名，
Writer 分批写入新表，最后在一个 SQL 事务中删除旧表、将新表改名并设置 SQL 版本。
这不是自动分析两份模型后生成 SQL，而是测试项目明确声明的 Task、Transfer、Check。
v3 只执行建索引和校验，不走数据转换管线；数据库内部仍需要扫描数据来构建索引。

`_n2x_receipts(id, digest)` 是本测试 SQL 适配器的操作提交凭证表，不是用户数据，
也不是 n2x 内核强制要求的表。每批写入或 SQL Task 都将业务变更与凭证放在同一个事务中。
如果数据库已提交、工作区进度尚未保存就退出，恢复时可以按相同 OperationId 和请求摘要核对：
有凭证就确认此前已提交，不重复执行；相同 ID 对应不同摘要则报错。
仅把凭证写进 `workspace/state.kv` 无法与业务 SQLite 事务原子提交，因此不能替代这里的凭证。
其他适配器可以用目标系统的幂等键、提交记录或可核验的幂等操作实现恢复，不必使用这张表。

## 大数据适用范围

**当前网页适配器只用于小数据演示，不是大数据读取实现。** 管线每批处理 2 条用于观察提交边界，
但测试 Reader 每次会完整读取 JSON、SQL 结果或目录文件，再切出本批，并计算整个源的摘要。
网页状态查询也会读取全部演示行和文件内容。批大小为 2 不意味着这些读取只占用两条记录的内存。

框架已经定义游标、批大小与字节上限、逐批写入和持久检查点。接入大数据时，Reader 必须在源头分页，
例如用稳定且有索引的主键执行下面的查询，并以本批最后一个主键作为下一游标，而非每次全表读取再切片：

```sql
SELECT id, first_name, last_name FROM users
WHERE id > :last_id AND id <= :source_upper_bound
ORDER BY id LIMIT :batch_size;
```

读取期间还需保证源一致性，例如冻结业务写入或使用可恢复的快照；最大主键上界本身不能阻止旧行被修改。
JSON / 大文件则应使用流式解析、可恢复偏移或分块引用。框架限制返回批次的大小，无法阻止适配器内部先分配全量内存。

同库且能用 SQL 表达的转换可以直接交给数据库执行，无需把所有行读到 Rust。
少量数据可作为一个 SQL Task；超大量数据应按可恢复的主键范围分批执行数据库内转换，
将每批结果与提交凭证原子保存，成功后推进检查点，最后校验并切换表。
这个姓名合并示例对应的单批数据库内转换可以是：

```sql
INSERT INTO users_v2(id, name)
SELECT id, trim(first_name || ' ' || last_name) FROM users
WHERE id > :start_id AND id <= :end_id;
```

这里展示的是适配器接入方式；当前演示仍保留 Rust Transform 来验证跨源转换管线，没有实现上述大数据 SQL 适配器。

## 自动测试

```sh
cargo test -p n2x-migration-lab
```

每个测试使用独立临时目录，避免改动网页的 data。覆盖逐版、直达 v3、反向请求、
事务回滚后继续、提交窗口重开、逐命令边界重开、暂停/取消和源视图变化。
逐命令边界测试会执行多轮真实持久 IO，耗时通常约一分钟。
